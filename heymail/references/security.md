# 安全封装的范围

## 三类数据分别保存

| 数据 | 保存位置 | 是否进入公开包 |
| --- | --- | --- |
| 技能说明、脚本、原创示意图、虚构测试 | GitHub 仓库 | 是 |
| 姓名、邮箱、简历路径和出勤资料 | `%LOCALAPPDATA%/HeyMail/config.json` | 否 |
| SMTP 客户端授权码 | Windows 凭据管理器，普通凭据 | 否 |
| 真实 JD、简历副本、正文与回执 | 各聊天的本机工作区 | 否 |

授权码不是注册验证码，也不是网页邮箱登录密码。技能不需要拥有邮箱网页密码；服务商生成授权码时的验证码、短信或扫码由用户亲自操作。

## 密码框和凭据

首次输入使用 `credential_input.py` 的 Tkinter 密码框，不需要提前提供邮箱；图形环境不可用时通过本机终端的 getpass 隐藏输入。终端模式拒绝管道输入，禁止降级为明文回显。旧的 `save-credential.ps1` 仅为已有账号更新凭据保留，不再作为首次弹框的必需组件。

第一步通过系统 CredWrite 将授权码保存到随机的 `HeyMail/pending/...` 普通凭据，用户名暂记为 pending。步骤文件 onboarding.json 只记录供应商、目标名称及进度。后续简历、邮箱到齐时，setup 在本机内部将授权码绑定到发件账号，写普通配置成功后删除对应 pending 凭据。被中断的首次配置可按步骤继续，不必再次发送授权码。

临时非托管写入缓冲区会清零释放；不会把授权码写到状态文件、JSON、终端输出或环境变量。Python 字符串和编码的临时副本仍受下述内存保护边界限制。

发送脚本调用 CredRead，仅在本机内部取出相应账号的授权码，使用完后释放引用。Windows 负责静态存储保护；Python 的字符串和 SMTP 库可能短暂保有明文内存，不能保证立即擦除。这里的“安全保存”不表示能抵御当前用户下的所有恶意程序、内存读取或管理员。

不要录屏或截图显示真实授权码；不要把它粘进聊天、GitHub issue、终端命令或网页表单。本项目不会要求用户把授权码发给开发者。如果误公开，立即在邮箱网页中撤销旧码并生成新码，仅删除聊天内容或 Git 提交不能使旧码失效。

## 发信通路

SMTP 只连接固定的 `smtp.163.com:465` 或 `smtp.qq.com:465`，使用系统信任链验证 TLS 证书，不提供跳过证书验证的选项。未知供应商/不匹配的发件地址会被拒绝，JD 无法指定服务器。

脚本构造正文和附件，不附加 AI 落款或 Agent Mail 页脚。服务商自身的风控或收件端显示不由本项目控制，因此不能保证没有垃圾箱拦截、退信或第三方客户端提示。

## 预览、确认和防重复

准备阶段离线，不读取授权码。预览对应不可变清单与全部附件哈希；“发送”只用于本聊天最新的已展示版本。改稿、改收件人、改发件人、添加或改动任一附件都需要新预览、新确认。

附加材料只有在用户明确指定后才加入。`additional_attachments` 中的源路径仅用于本机读取；公开仓库仅包含程序与虚构测试，不上传用户课题、简历或附件。发送前会逐个重新校验主简历和其他附件的哈希。

脚本在发出 DATA 前先保存 submitting 回执，发出后记录 accepted / rejected / uncertain。进程或网络在关键时间中断时保留可能发送的状态，优先阻止重复投递，而不是为了显示成功自动重试。

摘要提供一致性校验，不是防御本机恶意用户的数字签名；本机攻击者若能同时改程序、清单和摘要，不在该机制的保证范围内。保护依赖于可信本机环境和 Agent 正确执行用户确认规则。

## 提交到 GitHub 前

共享投递台账、投递事件、JD归档和人工更新均为本机私有资料，不提交到GitHub。记录Agent和岗位元数据不会改变邮件正文或附件；台账失败不改变SMTP已接受的结果，也不能触发邮件重发。

只上传技能仓库目录，检查文件清单、暂存区及提交内容。绝不把整个聊天工作区 `git add` 后上传。忽略 config、真实 PDF/DOCX、草稿、回执、日志与缓存；不提交密钥，也不通过读取凭据来执行“密钥扫描”。该工具没有遥测和远端凭据同步功能。
